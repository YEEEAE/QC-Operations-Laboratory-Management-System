# QC360 controlled change application technical source

Date: 2026-10-08. Source scope: REQ-CHG-005/006/007 and REQ-DATA-024.
Authority: the workspace owner requested implementation of the missing requirements and creation of their sources in this chat. This technical implementation source records that authorized scope. It is not an electronic signature, human UAT record, scientific approval, or document effectivity approval.

An APPROVED change request authorizes an application attempt only. APPLIED requires a successful owning-domain operation. For DOCUMENT_VERSION the supported scope is one text metadata change to revision or changeSummary on the exact captured DRAFT version, through Documents draft editing and its existing permissions. APPROVED, EFFECTIVE, superseded and other historical versions cannot be edited. Changes to those versions require a separately authorized revision and the existing controlled approval/effectivity workflow; this implementation does not infer that policy.

Application requires explicit scoped PERM-CHG-APPLY in addition to CHG view and the owning Documents edit permission. Current grants are rechecked under lock, including replay and safe failed-attempt evidence. APPLIED is admitted only for a persisted successful replay; it cannot start a new application.

Request state/version, target version/content hash/document identity/state and captured current value are checked under shared row locks. Document identity locks precede version locks, matching the owning Documents revision workflow. Documents mutates its target and appends its audit/outbox in the same transaction as the request START_APPLY/APPLY_SUCCESS, application success evidence and request audit/outbox. Any failure rolls back this transaction. Approval evidence remains preserved. A replay with the same request ID and original expected version returns the persisted success; a conflicting replay is denied. Safe stale-target or invalid-state failures record sanitized FAILED attempt evidence after rollback while retaining APPROVED; permission denials do not create application evidence. Controlled-version revision application remains an acceptance gap; a failed command must never be presented as APPLIED.

Verification scope: focused automated synthetic tests and local source checks are technical evidence only; PostgreSQL rollback/race, authenticated native POST, accessibility and human acceptance require their own evidence. Existing signature and effectivity gates remain authoritative.
