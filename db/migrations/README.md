- Files are forward-only SQL and are immutable after application to a shared environment.
- `scripts/db/migrate.ts` requires a contiguous four-digit source sequence, verifies the applied ledger is an exact source prefix (including names and current or explicitly retained legacy SHA-256 checksums), rejects duplicate versions, requires PostgreSQL 18.x, takes a PostgreSQL advisory lock, and applies each migration plus its ledger row in one transaction. Unknown checksums, reordered/skipped history, and incompatible server versions fail closed. The runner never updates or deletes an applied ledger row or rewrites a historical migration body.
- `scripts/db/migrate.ts --check` verifies drift without creating the schema or requiring DDL privileges; the advisory lock is still taken for a consistent ledger read.
- Migration execution is an operator-only CLI action; application startup, read-only health probes, and runtime preflight do not apply migrations. A SQL failure rolls back that migration and stops the run. If the connection is lost during commit/rollback, the outcome is reported as unknown and operators must inspect the read-only ledger and schema before retrying.
- A checksum mismatch is a hard failure. Repair is represented by a new migration, never by editing history.
- `DATABASE_URL` is the pooled application runtime principal. The migration CLI requires `--direct` and prefers the operator-only `DATABASE_URL_UNPOOLED`; `MIGRATION_DATABASE_URL` is a compatibility alias only when it agrees with the direct URL. There is no fallback to `DATABASE_URL` and the CLI rejects pooled endpoints. The migration principal must be distinct from the runtime principal and identify the same configured database target.
- Production use is denied unless the command explicitly includes `--production-approved` and runtime configuration supplies `MIGRATION_PRODUCTION_RELEASE_ID` plus `MIGRATION_PRODUCTION_APPROVAL_REFERENCE`. These values provide an operator-supplied release context; they do not independently prove an approval in the release-governance system. Keep the context traceable to the separately approved release/change record.
- In dedicated-principal deployments, the runtime principal should not have database/schema `CREATE` or write access to `qc.schema_migrations`; the migration principal needs separately approved DDL and ledger rights. `db:preflight` reports runtime capability only and never opens `MIGRATION_DATABASE_URL`. Use the permission template in `db/README.md` separately for each principal; source support does not establish provider grants or role separation.
- Migration ownership checks remain fail-closed. No automatic ownership transfer or role creation is performed by the application credential.
- The runner accepts the exact legacy checksums from the former role/ownership model so an existing ledger is not silently rewritten. If such a database has pending migrations, the runner fails closed until a provider administrator remediates ownership; it never transfers ownership or creates roles from the application credential.

The first migration creates only shared database primitives and identity/platform infrastructure. Domain tables are introduced by later, separately reviewed migrations.

Migration 0053 validates the four receiving-normalization checks introduced as `NOT VALID` in 0035. It performs no historical backfill: a historical violation aborts the migration and requires a separately authorized disposition. None of these source migrations is asserted to be applied to any database.

The source workflow for `NOT VALID` constraints is: introduce a reviewed constraint as `NOT VALID` to enforce it for new or changed rows without immediately scanning all historical rows; identify existing violations through separately approved read-only inspection; obtain an explicit disposition for each invalid historical value; then add a later forward-only migration using `VALIDATE CONSTRAINT`. Do not invent defaults, silently backfill values, or weaken the constraint to make validation pass. The outstanding `NOT VALID` source constraints before applying 0053 are `qc.receiving_items.receiving_items__quantity_unit_vocabulary`, `receiving_items__expiry_not_before_receiving`, `receiving_items__purchase_order_no_not_blank`, and `receiving_items__source_reference_not_blank`. Migration 0053 is the controlled validation step; no legacy value is rewritten. Actual database validation state remains unknown until an authorized operator inspects it.

Review table locks, unique constraints/indexes, scan duration, and historical-data consequences with the database owner before scheduling a change. This runner wraps each complete migration and its ledger insert in one transaction; migrations needing unsupported non-transactional DDL require a separately designed and approved runner workflow before such a migration is added.
