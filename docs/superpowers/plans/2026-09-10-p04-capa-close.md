# P-04 CAPA Close Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the approved Supervisor-only CAPA close path with explicit permission, scope, active-account, version, reason, reauthentication, CLOSE signature, idempotency, exact snapshot, transactional audit, UI ceremony, and regression tests.

**Architecture:** Keep the existing generic CAPA transition path for ACTIONS_COMPLETE and effectiveness transitions. Add a dedicated `CloseCapaUseCase`, a repository `close` command, and a CAPA-specific ceremony/dependency wiring that owns the P-04 exception without weakening other transitions. The repository transaction is the only place that commits the CAPA update plus snapshot/signature/audit/idempotency evidence.

**Tech Stack:** Astro Actions, TypeScript, Kysely, PostgreSQL, Vitest, existing authorization/audit/e-signature/outbox infrastructure.

### Task 3: Add dedicated application use case and ceremony contract

**Files:**
- Create: `src/modules/quality/capa/application/close-capa.ts`
- Modify: `src/modules/quality/capa/ports/repository.ts`
- Modify: `src/modules/quality/capa/application/transition-capa.ts` only to leave CLOSE out of the generic execution path or delegate explicitly without changing other actions.

- Test: `tests/unit/quality/capa-close.test.ts`

- [ ] **Step 1: Define the close repository contract.**

Add `findReplay(requestId, subjectId)` and `close(input)` with:

```ts
close(input: {
  id: string;
  expectedVersion: bigint;
  actor: ActorContext;
  reason: string;
  requestId: string;
  signatureId: string;
}): Promise<Capa>;
```

The repository owns snapshot/audit/signature/idempotency persistence and must not accept a client-declared next state.

- [ ] **Step 2: Define the dedicated use-case input and dependencies.**

The use case accepts `actor`, `id`, `expectedVersion`, `reason`, `reauthenticationSecret`, and `requestId`, plus a ceremony dependency exposing `verifySignature` with action `CLOSE`, explicit meaning, subject version, snapshot reference, reason, and request ID.

- [ ] **Step 3: Implement authorization in the required order.**

Use `AppError` stable codes. Reject unless `actor.roles` contains canonical `SUPERVISOR`, the account is active, and the actor has active `PERM-CAPA-CLOSE`. Then call `authorize` with CAPA entity/state, owner/created scope, current/expected version, and `businessCondition` restricted to the P-04 eligible states. Do not grant Admin or SYSTEM_OWNER bypass.

- [ ] **Step 4: Validate reason and invoke the ceremony.**

Reject blank/whitespace reason before ceremony. Use exact meaning:

```text
Close CAPA ${current.capaNo}, version ${expectedVersion}
```

Use the server-derived snapshot reference from the current CAPA/version; never use a client snapshot. Missing/failed reauthentication or signature must prevent repository mutation.

- [ ] **Step 5: Add application tests for all required branches.**

Cover Supervisor positive with incomplete actions/effectiveness false, Employee, Manager, Admin-only, yazeed without Supervisor, missing permission, wrong scope, inactive account, stale version, blank reason, failed reauthentication, missing signature, terminal state, and duplicate replay. Assert repository `close` is not called on every denied path and that replay returns the prior result without a second ceremony/mutation.

- [ ] **Step 6: Run the focused application tests.**

Run: `pnpm exec vitest run tests/unit/quality/capa-close.test.ts tests/integration/quality/capa.test.ts`

Expected: all dedicated close tests pass and the generic transition tests remain green.

### Task 4: Implement the PostgreSQL transactional repository path

**Files:**
- Modify: `src/modules/quality/capa/infrastructure/postgres-repository.ts`
- Inspect/modify as required by existing schema contracts: `src/shared/audit/postgres-audit-repository.ts`, `src/modules/e-signatures/infrastructure/postgres-repository.ts`, `src/shared/outbox/postgres-outbox-repository.ts`, `src/shared/database/db-types.ts`
- Add migration only if the existing schema lacks a CAPA snapshot/idempotency representation; do not edit historical migrations.
- Test: `tests/integration/quality/capa-close-postgres.test.ts`

- [ ] **Step 1: Read and lock the CAPA row inside one transaction.**

Use Kysely transaction scope and `FOR UPDATE`/equivalent. Revalidate `id`, `expectedVersion`, current state, actor-visible scope, and terminal state against the locked row. Capture the complete exact pre-transition CAPA and action rows needed for the snapshot before updating anything.

- [ ] **Step 2: Make request replay deterministic.**

Look up an existing successful close by request ID and CAPA subject before creating evidence. Same actor/subject/request returns the stored result. A request ID reused for a different subject/action must fail safely rather than cross-apply.

- [ ] **Step 3: Commit the state change and evidence atomically.**

In the same transaction:

```text
insert exact pre-transition snapshot
update capas state=CLOSED, closed_at=trusted DB time, version=version+1
persist signature evidence reference/record
insert immutable audit event with TR-CAPA-006, versions, reason, request_id, signature_id
insert idempotency result/reference and required outbox event if the existing CAPA pattern requires it
commit
```

On any failure, rollback all writes. Map zero-row version updates to `CONFLICT_STALE_VERSION`, terminal state to a stable state error, and duplicate/replay according to the use-case contract.

- [ ] **Step 4: Add PostgreSQL integration assertions.**

Against disposable PostgreSQL, prove successful close increments version, preserves the exact pre-transition snapshot, creates one signature/audit/idempotency record, and does not duplicate evidence on replay. Prove stale and terminal requests do not mutate CAPA. Add rollback coverage by forcing an evidence insert failure and asserting CAPA remains unchanged.
